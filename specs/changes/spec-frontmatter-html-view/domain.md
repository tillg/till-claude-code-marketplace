# Domain: spec frontmatter and HTML view

## New concepts

### Feature
The unit of work a change directory describes. Its **name** is the kebab-case change name
and equals the directory name (`specs/changes/<feature>/`).

### Feature status
Where the feature is in the lifecycle. One value per feature, repeated in every artifact of
the change (skills always update all of them together; lint flags disagreement).

| Status | Set by | Meaning |
|---|---|---|
| `exploring` | `/spec:explore` when it writes notes into a change dir | idea stage, artifacts incomplete |
| `proposed` | `/spec:propose`, `/spec:iterate` | all four artifacts exist, not started |
| `applying` | `/spec:apply` on its first completed step | implementation in progress |
| `paused` | the user (by hand or asking Claude) | parked on purpose |
| `applied` | `/spec:apply` when every plan step is `[x]` | done, ready to archive |

`/spec:archive` removes the change directory, so there is no `archived` value in a change;
system docs (`specs/system/*.md`) have no `feature` or `status`.

### Spec frontmatter
Closed schema, keys in this order. It says nothing about which *kind* of file it is: the
build never needs to know that a file is "the proposal".

| Key | Required | Meaning |
|---|---|---|
| `feature` | yes (change files) | the feature name = directory name |
| `title` | yes | the page title (usually the existing `# …` heading text) |
| `status` | yes (change files) | a feature status (above) |
| `order` | no | integer; position in the group's nav (lower first). The spec skills write 1–4 for proposal, domain, architecture, plan |
| `created` | yes | ISO date |
| `edited` | yes | ISO date, set by the author when content changes |

The body keeps its own `# Title` heading, so the `.md` still reads well on GitHub.

### Spec profile (md2html)
A second rendering profile next to **report**. Sources: `specs/**/*.md` by default.
Differences from reports: spec frontmatter schema, no section numbering, no hoisted TL;DR,
**inner navigation** instead of the reports menu bar, Mermaid fences rendered by a script,
`fmt` never applied, output gitignored.

### Group
All spec-profile `.md` files in one directory, e.g. `specs/changes/add-x/`. Discovered by the
build from the directory listing; no file names are special. Ordered by `order`, then file
name.

### Inner navigation
The bar at the top of a spec page: an **up** link to the project index, then one link per file
of the group (label = file name without `.md`, dashes → spaces, capitalised: `risks.md` →
"Risks"), the current one marked, plus the feature's status pill.

### Project index
`index.html` in the project root, generated: one row per group (directory path, feature and
status if its files have them, title of its first file, newest `edited`, links to every page).
It is only written if the file doesn't exist or was generated by md2html, so a project's own
`index.html` is never overwritten (then the path is set in config).

### Spec viewer
The watcher (`md2html build --watch`) plus a local HTTP server, started by `/spec:view`.

## Vocabulary

| Term | Meaning |
|---|---|
| Feature | a change, named like its directory |
| Feature status | `exploring` · `proposed` · `applying` · `paused` · `applied` |
| Spec profile | md2html's rendering rules for spec files |
| Group | the spec files of one directory, discovered by the build |
| Inner navigation | per-group nav bar with an "up" link |
| Project index | generated `/index.html` listing all groups |
